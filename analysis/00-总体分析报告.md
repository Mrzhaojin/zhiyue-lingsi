## 0. 一页结论

**它是什么**：一个「阅读 + 社区 + AI 助手」的单页应用，30 个页面（36 条路由）、8 个数据域，界面完成度不低，主流程可以点通——**前提是你先自己建一个 Supabase 项目并配好环境变量**。

**它不是什么**：不是一个有后端的平台。所有帖子、评论、笔记、收藏、阅读记录都只存在浏览器 localStorage 的一个 JSON 字符串里；Supabase 只承担登录；仓库里另有一整套近 2000 行的自研认证服务端（`src/modules/auth/server`），**前端从未调用过它**。

### 真实完成度（主观评分，10 分制）

| 维度 | 分数 | 一句话判断 |
|---|---|---|
| 产品 / 页面完成度 | **8** | 26 个业务页 + 4 个认证页，交互密度高，视觉统一 |
| 前端代码质量 | **6** | TS strict 全过、领域类型完整；但无状态层、巨型组件、约 600 处内联样式 |
| 数据层 | **2** | 单 blob 全量读写、无订阅、无分页、无迁移、无配额处理 |
| 安全 | **2** | 真实 API Key 硬编码且已进公开 git 历史；RLS 从未执行；权限恒空 |
| 工程保障 | **2** | 0 个测试、0 CI、README 是 Vite 模板 |
| 文档可信度 | **1** | `项目文档.md` 里的数据库/并发/跨端/测试结论，与代码大面积不符 |

### 三个最致命的问题

1. **密钥已经泄露**：`src/services/ai.ts:7,99` 明文硬编码火山方舟 API Key，随提交 `9c7e04a` 进入公开仓库，并在 `ai.ts:20` 打印密钥前后各 5 位；静态部署后也会出现在 JS bundle 里。**这不是风险，是已发生的事实。**
2. **新克隆跑不起来**：仓库没有 `.env`。缺配置时 `supabase.ts:20-33` 启用 mock 客户端，`signInWithPassword` 返回 `error:null` 但永远不会建立会话；`AuthProvider.tsx:193-217` 把状态置为 `loading` 后再也不恢复，`RequireAuth.tsx:9` 让整个应用停在「加载中...」。
3. **身份与数据是两套**：登录身份是 Supabase UUID，内容归属却是种子数据里写死的本地用户（`db.ts:1147`，`getCurrentUser()` 永远返回它）。结果：换账号看到同一份数据、个人统计恒为 0、AI 对话历史永远为空、点赞在首页和详情页状态不一致。

### 为什么值得重构，而不是推倒重来

页面和交互是真资产：阅读器的选区菜单（`ReaderPage.tsx:189-204`）、AI 赏析抽屉、笔记模板与分享卡、社区楼中楼、双 Shell 响应式，都是实打实写出来的。缺的是**数据层、身份闭环、工程证据**——而这三块恰好是保研/考研面试最认的「工程判断力」，也是最能讲出深度的部分。

重构后可以讲一个完整故事：**发现 MVP 数据方案的边界 → 设计可迁移的 Repository → 用指标证明迁移收益**。这比「我做了 30 个页面」有分量得多。

## 3. 分层诊断

> 本节给结论与最硬的证据；完整证据链见四份深潜报告。

### 3.1 数据层：整库 JSON，读改写无边界（详见 01）

**结论**：没有数据库。唯一持久化是 `localStorage['read_forum_db_v5']` 里的一整个 JSON，`version` 字段却是 4（key 与版本号已经漂移）。所有 getter 都先 `JSON.parse` 整库，所有 mutation 都「读整库 → 改内存 → 写整库」。

最狠的五条证据：

1. **读操作带写副作用**：版本不符或解析失败直接 `createSeedDb()` 覆盖（`db.ts:1246`）；种子补丁在每次读取时检查并可能写回（`db.ts:1238-1250`）。一次数据损坏 = 全部用户内容无提示清零。
2. **写放大且无配额处理**：`writeStorage` 没有 try/catch（`storage.ts:18-22`）；图片和分享卡以 dataURL 原样入库（`NewPostPage.tsx:9-22`、`NoteEditorPage.tsx:401-412`），一张 2x PNG 分享卡 + 9 张手机照片就能击穿 5MB，`QuotaExceededError` 抛出后用户只看到页面没反应。
3. **没有订阅，数据变了 UI 不知道**：全仓无 `storage` 事件、无 `BroadcastChannel`、无 `useSyncExternalStore`、无 store；写库后组件不重渲染（ToastProvider 的 children 是同一个 element 引用，Context value 稳定 → React bailout）。作者用 `navigate(0)` / `window.location.reload()` 兜底了 3 处。
4. **身份双源**：`currentUserId` 只在种子数据里赋过一次值（`db.ts:1147`），全仓没有第二个写入点。所有内容都归这个演示用户，与登录账号无关。
5. **查询全是内存全表扫描**：所有 `list*` 都 `Object.values(全表)` 再排序，无分页、无索引、无游标；首页一次渲染要解析整库 6 次（`HomePage.tsx:25-38`）。

**种子数据的额外问题**：14 本书、26 个章节，但三类内容混用——经典原文摘段、改写概述、以及 **AI 生成且与原著情节不符的伪章节**（如《三体》「红岸基地」章、《红楼梦》第二回把甄士隐与贾雨村写成官驿相会）。部分计数与真实记录矛盾：post5 显示 42 条评论，实际库里 2 条；用户「书海泛舟」显示 25 篇帖子，实际 1 篇。

**可讲的真亮点（很少）**：interaction 用 `${userId}:${kind}:${targetType}:${targetId}` 复合键做幂等去重（`db.ts:1531-1565`），点赞/收藏切换天然可重入——这是数据层唯一一处有设计感的代码。

### 3.2 认证与安全：三套身份、两套认证、一条活链路（详见 02）

**结论**：前端只走 Supabase Auth；仓库里另有一整套 Express 5 + JWT + bcrypt + Postgres 的自研认证服务端（`src/modules/auth/server`，1900+ 行），以及一套 Bearer + HttpOnly 刷新令牌模型的客户端 `authApi.ts`（206 行）——**两者都是死代码，0 调用**。

这套死代码本身质量不差：bcrypt cost=12、refresh token 只存 sha256、事务内轮换、jti 黑名单、每请求从 DB 读 RBAC、step-up 二次验证、审计日志。但它**从未被端到端跑通**：`/stepup` 引用了未定义的 `jwt`（`index.mjs:486`），而封禁/解封又强制要求 step-up，必然失败。

安全面的五个 P0：

| 编号 | 问题 | 证据 |
|---|---|---|
| 密钥泄露 | 方舟 Key 硬编码 + 打印 + 进 git 历史 + 公开仓库 | `ai.ts:7,99,20`；`git log -S` 命中 8 个提交 |
| 假登录 | 无 env 时 mock 返回 `error:null`，状态卡 loading | `supabase.ts:20-55`、`AuthProvider.tsx:193-217` |
| 找回密码断链 | `redirectTo` 指向不存在的 `/zhiyueling-si/password/reset` | `AuthProvider.tsx:288` vs `App.tsx:68-75` |
| 密码被转义 | 登录时对密码做 HTML 实体编码，注册时不编码 → 含 `& < > '` 的密码永久登录失败 | `LoginPage.tsx:147-148` vs `RegisterPage.tsx:147` |
| RLS 是纸面安全 | `rls.sql` 全仓 0 引用、从未执行；即使执行，策略允许 anon 插 users、行主自改 status，`user_roles` 策略还会无限递归 | `rls.sql:9-10,47-48,60-67`；`db.mjs:63-82` |

另外：`permissions` 在 AuthProvider 里硬编码为 `[]`，`/admin` 永远 403；真正被后台修改的是 localStorage 里的敏感词/置顶配置 —— 用户改本地存储即可绕过内容审核。

### 3.3 前端架构与 UI：有设计品味，没有设计系统（详见 03）

**结论**：这是一个「用 React 渲染的 localStorage 客户端」。页面看起来完整，但 10+ 处交互点完界面不变（书架移除、删单词、全部已读、调字号、加敏感词……），因为写库不会触发重渲染。

结构性问题：

- **双响应式真源**：JS 用 `window.innerWidth < 768` 选 Shell（`App.tsx:47-62`），CSS 也用 768px 断点；跨断点时整棵 React 树卸载重建，表单草稿、滚动位置、阅读器状态全部丢失。
- **全量静态导入**：30 个页面 + Quill + html-to-image + supabase-js 全进入口 chunk，`React.lazy`/`Suspense` 出现 0 次；构建产物 708KB 单 chunk，与文档声称的「代码分割、懒加载」相反。
- **样式是追加式覆盖**：`App.css` 1366 行，同一选择器重复定义 13 组，`.grid` 两套规则互相冲突；3 个认证页在模块加载时向 `document.head` 注入 `<style>`（合计 96 处 `!important`）；TSX 里约 600 处内联样式、97 处硬编码色值。
- **无障碍系统性缺失**：`role=` 全仓 0 处；可点击 div/span 遍布；模态无 `dialog` 语义/焦点陷阱/Esc；实测对比度 `--accent` 文字 1.92:1、`--muted` 2.02:1（AA 要求 4.5:1）；`<html lang=en>` 但全站中文。
- **重复代码**：`getAvatarColor` 复制 5 份、头像渲染块至少 15 处、`readFilesAsDataUrls`/`downloadText`/`parseTags` 各 2 份、两套 SearchIcon。

**性能基线**：首屏 JS 708KB（gzip 210KB）+ 封面图单张 0.9–2.0MB（首页一次渲染 8 张）；无分页、无虚拟列表、无 `React.memo`。数据量一涨就会崩，但当前种子数据小，问题被掩盖。

### 3.4 AI 能力：两条真链路，其余是表演（详见 04）

|---|---|---|

### 3.5 工程与交付

- **无测试、无 CI**：`package.json` 只有 dev/build/typecheck/lint；仓库无 `.github`，无任何 `*.test.*`。

## 5. 为什么「没得奖」——诚实归因

不是运气问题，是评审视角下的结构性短板：

1. **作品叙事与实现脱节**。计算机设计大赛的评审会按文档核对。文档写 MySQL、跨设备同步、100+ 并发、全部测试通过，代码里是 localStorage 单机 demo、0 测试、无后端——这是最致命的一条，一旦被问就全盘失分。
2. **「平台」不成立**。社区类作品的核心是多人数据与权限；这个项目没有服务端业务数据，所有人看到的是各自浏览器里的平行世界。评委问一句「两个用户怎么看到彼此的帖子」就结束了。
3. **AI 是调用而非能力**。硬编码 Key + 裸调 + 无上下文 + 模板兜底，属于「接了个 API」，不构成技术贡献；而真正能讲的检索增强、评测、成本治理一个都没有。
4. **缺少工程证据**。无测试、无性能数据、无部署架构、无监控；只有页面截图。评审无法判断「这代码是你写的、能维护」。
5. **选题同质化**。「阅读社区 + AI 助手」是烂大街组合，没有一句话能让人记住的差异化。
6. **完成度其实是优势，但没有被组织成优势**。30 个页面、阅读器交互、双端布局，这些是真实工作量；只是被塞进了「平台」的叙事里，反而暴露了数据层的空。

**可救的部分**：产品直觉、页面完成度、交互细节、TS 工程习惯。**要补的部分**：数据层、身份闭环、工程证据、诚实的叙事。这也正好是这次重构的目标。

## 6. 重构定位与目标架构

### 6.1 定位：从「阅读论坛平台」改成「离线优先的 AI 阅读工作台」

三个候选方向：

| 方向 | 一句话 | 技术含量 | 风险 |
|---|---|---|---|
| A. 离线优先（Local-first） | 数据先落本地，多端同步可恢复 | 高：仓储抽象、迁移、冲突合并、同步引擎 | 中：要讲清一致性与冲突策略 |
| B. AI 阅读助教（RAG） | 基于书库/笔记的检索增强问答 | 高：切分、检索、引用、评测 | 中高：需要真实语料与评测集 |
| C. 社区推荐系统 | 行为数据驱动的个性化推荐 | 中高：协同过滤、冷启动、离线评测 | 高：种子数据太少，效果难证明 |

**推荐 A + B 组合**：底层做 Local-first 数据层（这是最能体现工程判断的部分），上层做 RAG 阅读助手（这是最能体现 AI 应用能力的部分）。C 可以作为 A 的副产品（用已有 interactions/shelves 做 item-based CF + 离线 nDCG 对比热度基线），但不要当主线。

一句话定位：**「一个离线可用、可迁移、带检索增强阅读助手的个人阅读工作台」**。不再是平台，不承诺并发与多人协作——这反而让每个技术点都能讲透。

### 6.2 设计原则

1. **单一真相**：`auth.uid` 是唯一用户身份；计数由数据派生或事务维护，不手工 ±1。
2. **可迁移**：存储实现可替换（IndexedDB ↔ Postgres），迁移与备份是一等公民。
3. **页面不碰存储**：页面只消费 hooks，`src/pages/**` 禁止 import 数据实现（用 ESLint `no-restricted-imports` 强制）。
4. **失败可见**：所有写操作有错误路径与用户提示；AI 失败不得伪装成成功内容。
5. **可测可证**：每个结论都有命令、指标或测试能复现。

### 6.4 关键技术决策（ADR 摘要）

| 决策 | 选择 | 理由 | 放弃的方案 |
|---|---|---|---|
| 状态管理 | TanStack Query + 少量 context | 缓存/失效/重试/乐观更新开箱即用，面试好讲 | Redux（过重）、Zustand（仍要自己写缓存） |
| 本地存储 | Dexie/IndexedDB，一实体一表 | 事务、索引、大对象，替换单 blob | 继续 localStorage（5MB + 无事务） |
| 云端 | Supabase Postgres + RLS + Storage | 已有登录，省运维；RLS 是很好的面试素材 | 自建 Postgres（面试前没时间运维） |
| 认证 | 只保留 Supabase Auth；删自研服务端 | 两套并存是最大减分项 | 保留自研（需自己修 1900 行 + 部署） |
| AI 代理 | 单 Node BFF（复用现有 Express 骨架） | 本地可跑、可演示、可加限流/缓存/评测 | 纯前端直连（已证明不可行） |
| 测试 | Vitest + RTL + Playwright + 黄金集 | 单元/契约/端到端/AI 质量四层 | 只写单测（证明不了链路） |

### 6.5 明确不做（避免过度设计）

- 不上微服务、不上向量数据库做全库 RAG（书只有 14 本，BM25 + 上下文注入足够；要做 pgvector 也只作为加分项）；
- 不上 WebSocket 实时协作（没有多人场景，讲不清收益）；
- 不重写 UI 视觉（保留现有奶白/薄荷绿语言，只抽 token 与组件层，「增量重构」本身是好故事）；
- 不保留任何「假延迟 / 随机洗牌 / 999+ 条」的表演型代码。
