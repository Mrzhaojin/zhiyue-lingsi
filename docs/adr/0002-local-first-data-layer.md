# ADR-0002：本地优先数据层（IndexedDB + Repository）

- 状态：已采纳并实施（M1 完成）
- 日期：2026-11-27

## 背景

当前所有业务数据存在 `localStorage['read_forum_db_v5']` 的单个 JSON 里：

- 读：每次 getter 都 `JSON.parse` 整库；
- 写：每次 mutation 都序列化整库，无事务、无锁；
- 图片与分享卡以 dataURL 入库，5MB 配额必然击穿；
- 无订阅：写库后 UI 不重渲染，10+ 处交互「点了没反应」；
- 解析失败或版本不符会直接重建种子库，等于静默丢数据。

## 决策

1. 引入 `Repository` 作为唯一读写口，页面只消费 hooks；
2. 本地适配器使用 **Dexie/IndexedDB**：一实体一表、事务、索引、Blob；
3. 旧数据通过**版本化迁移器**导入：zod 校验 → 逐表写入 → 条数/字段抽检 → 保留只读备份；
4. 图片压缩（长边 ≤1280、WebP，目标 ≤200KB）后存 Blob 表，记录只存 id；
5. 跨标签页用 `BroadcastChannel` 广播失效，杜绝「A 改了 B 不知道」；
6. 云端适配器（Supabase）后续接入，接口不变。

## 后果

- 单次写入只影响一张表，不再整库序列化；
- 数据量增长后仍可索引查询、分页；
- 迁移与备份成为一等公民，可解释、可验证；
- 成本：需要维护两套适配器与迁移测试；团队只有一人时，优先完成 LocalAdapter。
- 实施备注：为了保证 30 个页面的同步读取不被一次性改坏，M1 采用「内存快照 + 实体级写入 + 版本订阅」：
  页面读到的是内存对象，写入通过 `mutate(db, ctx)` 登记精确的 put/delete，再由 Dexie 事务落盘。
  这样既没有整库序列化，也不需要先重写全部页面；M1.5 再把页面换成查询 hooks。

## 验收（写进 M1）

- 1000 条记录迁移 0 丢失，字段抽检 100% 通过；
- 任意写操作后 UI 一帧内更新；
- 双标签页并发写 100 次不丢记录；
- 配额不足时有明确提示且不破坏已有数据。

## 备选方案

- **直接换成 Supabase**：跨网络、依赖服务端，无法离线演示；且仍然要解决迁移与订阅。
- **localStorage 加防抖/分 key**：能缓解写放大，但改变不了无事务、无索引、5MB 上限的本质。
